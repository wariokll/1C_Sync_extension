# Задание для ChatGPT: BSL и форма внешней обработки

Это руководство рассчитано на проект генератора внешних обработок в 1С. Оно просит ChatGPT реализовать уже согласованную логику и подготовить файлы в формате, который понимает `New-EpfFromDefinition.ps1`.

## Как использовать

1. Открой отдельный чат, где уже обсуждена логика обработки.
2. Вставь целиком блок «Промпт» ниже.
3. Вместо текста в квадратных скобках добавь из того чата утверждённую логику, ограничения и исходные данные. Если нужные сведения уже есть в переписке, попроси использовать её.
4. Передай ChatGPT примеры `epf-form-definition.example.json` и `epf-form-module.example.bsl`, а также `README-Генератор.md`, если можешь прикрепить файлы. В крайнем случае вставь их содержимое.
5. Сохрани полученные `.bsl` и `.json` рядом в папке проекта. В JSON укажи `modulePath` относительно файла JSON, например `"./МодульОбработки.bsl"`.
6. Запусти проверку по инструкции после блока промпта.

## Промпт для отправки

```text
Ты — опытный разработчик 1С:Предприятие 8.3, пишешь исполняемый BSL-код и формируешь управляемые формы внешних обработок.

Нужно реализовать логику ниже без изменения её бизнес-смысла и подготовить файлы для проекта генератора внешних обработок. Не переизобретай требования и не добавляй неоговорённое поведение. Если критически важные сведения отсутствуют или противоречат друг другу, сначала задай конкретные вопросы и дождись ответов.

Уже согласованная логика и требования:
[ВСТАВИТЬ СЮДА ПОЛНУЮ СПЕЦИФИКАЦИЮ ИЗ ОТДЕЛЬНОГО ЧАТА: ЧТО ДЕЛАЕТ ОБРАБОТКА, ИСТОЧНИКИ ДАННЫХ, ПРАВИЛА, ОТБОРЫ, ПРОВЕРКИ, ОШИБКИ, ОЖИДАЕМЫЙ РЕЗУЛЬТАТ]

Среда и ограничения проекта:
- Платформа 1С:Предприятие 8.3.27.2214.
- Это внешняя обработка, формы управляемые.
- Проект собирает форму из JSON-манифеста при помощи `New-EpfFromDefinition.ps1`.
- Посмотри приложенные `README-Генератор.md`, `epf-form-definition.example.json` и `epf-form-module.example.bsl`; соблюдай их фактический формат и ограничения.
- Не пиши XML формы вручную: XML и метаданные формы создаёт генератор из JSON.
- Не подменяй согласованную логику демонстрационным кодом, заглушками, псевдокодом или TODO.
- Не выдумывай имена метаданных, реквизитов, измерений, ресурсов, документов, перечислений, процедур платформы или методов. Используй только сведения из спецификации и приложенных материалов. Отмечай всё, что нельзя подтвердить.

Сгенерируй ровно два файла:
1. `МодульОбработки.bsl` — полный модуль формы на BSL, без пропусков.
2. `ОпределениеФормы.json` — валидный JSON-манифест для `New-EpfFromDefinition.ps1`, без комментариев и завершающих запятых.

Требования к JSON:
- Корневой объект содержит `forms` с одной или несколькими формами.
- У каждой формы укажи уникальное допустимое имя `name`, понятный `synonym`, `isDefault` только у одной основной формы, `modulePath`, `attributes`, `controls`, `commands` и `events`.
- `modulePath` укажи относительным путём от JSON к `МодульОбработки.bsl`, если все формы используют один модуль. Если модули разные, перечисли каждый созданный `.bsl` файл и укажи его путь.
- Поддерживаемые типы реквизитов: `String`, `Number`, `Boolean`, `Date`, `CatalogRef.ИмяСправочника`, `ValueTable` с колонками. Для строк и чисел указывай нужные длину/разрядность; для даты — `dateFractions` из `Date`, `Time`, `DateTime`, если требуется.
- Поддерживаемые контролы: `InputField`, `CheckBoxField`, `Table`, `Button`, `Group`. Группа содержит `children`, `direction` (`Vertical` или `Horizontal`) и необязательный `title`; группы можно вкладывать.
- Для каждого `InputField` и `CheckBoxField` создай реквизит с соответствующим типом. `CheckBoxField` допускается только для `Boolean`.
- Для каждого `Table` создай реквизит типа `ValueTable` и перечисли все её колонки с правильными типами и заголовками.
- Для каждой команды кнопки создай элемент в `commands`; поле `command` кнопки должно совпадать с `commands[].name`.
- `commands[].action` и `events[].handler` должны точно совпадать с именами процедур/функций в BSL-модуле. Для команд используй процедуры. Реализуй каждый обработчик, который объявлен в манифесте.
- Используй понятные русские заголовки реквизитов, колонок, групп и команд. Разложи интерфейс по шагам: параметры, действия, результат и сообщения/статус, если это оправдано сценарием. Связанные поля располагай рядом; для таблиц результата предусмотри нужные колонки.
- Не добавляй элементы интерфейса, которые не нужны для описанной логики. Не создавай фиктивные реквизиты и команды.

Требования к BSL:
- Выдай полный исходный текст каждого модуля. Соблюдай синтаксис платформы 8.3.27 и директивы компиляции клиентских/серверных процедур.
- Реализуй все команды и события из JSON. Имена процедур должны совпадать с `action` и `handler` посимвольно.
- Разделяй клиентскую и серверную логику по назначению и требованиям платформы. Не передавай на клиент то, что должно исполняться на сервере.
- Проверяй обязательные параметры и пустые выборки, показывай пользователю понятные сообщения. Обрабатывай ожидаемые ошибки так, чтобы пользователь понимал, что произошло; не скрывай диагностику и не используй пустые `Исключение`.
- Не используй несуществующие методы и свойства. Не называй переменные одной буквой. Не помещай исполняемый BSL в строку для динамического выполнения.
- Если код зависит от неизвестного имени метаданных, сначала запроси его у меня; не маскируй неизвестное имя произвольным предположением.

Формат ответа:
- Сначала кратко перечисли допущения и вопросы, если они действительно остались. Не выдавай код с неразрешёнными критическими допущениями.
- Затем покажи каждый файл отдельно: заголовок с точным именем файла и полный текст в отдельном fenced code block с языком `bsl` или `json`.
- Не сокращай код фразами «остальное без изменений», многоточиями или псевдокодом.
- После файлов перечисли соответствие команд/событий их обработчикам и дай короткий список проверок перед сборкой.
- Проверь JSON на синтаксическую корректность, соответствие ссылок на реквизиты и команды, уникальность имён элементов формы и наличие каждого обработчика в BSL.
```

## Проверка файлов в проекте

Положи оба сгенерированных файла в одну папку проекта. В PowerShell из корня `ЭкспортЦен` запусти проверку JSON и сборки XML без Конфигуратора:

```powershell
$module = (Get-ChildItem .\Forms -Recurse -Filter Module.bsl | Select-Object -First 1).FullName
.\New-EpfFromDefinition.ps1 `
  -ModulePath $module `
  -DefinitionPath .\ОпределениеФормы.json `
  -ValidateOnly
```

`-ModulePath` здесь указывает на существующую форму шаблона: скрипт проверяет, что её исходные обработчики остались совместимыми. Модуль новой формы указывается в JSON через `modulePath` и проверяется отдельно.

Если проверка прошла, собери `.epf` с установленным Конфигуратором версии `8.3.27.2214`:

```powershell
$module = (Get-ChildItem .\Forms -Recurse -Filter Module.bsl | Select-Object -First 1).FullName
.\New-EpfFromDefinition.ps1 `
  -ModulePath $module `
  -DefinitionPath .\ОпределениеФормы.json `
  -DesignerPath 'C:\Program Files\1cv8\8.3.27.2214\bin\1cv8.exe' `
  -OutputPath .\output\НоваяОбработка.epf
```

Проверка `-ValidateOnly` проверяет обработчики и корректность XML, но не заменяет компиляцию BSL и проверку формы в Конфигураторе и тестовой базе 1С.
